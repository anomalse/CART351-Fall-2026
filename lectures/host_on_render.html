HOSTING AND RENDER

Introduction

Preamble :What Is Flask's Built-in Server?

When you develop a web application with Flask, you need a way to test and preview it while you're building.
That's where Flask's built-in server comes in - which is the one we have been using until now :)
It lets you test your app locally without needing to set up anything complicated.

Flask's built-in server is powered by a tool called Werkzeug, which handles the basic functionality of a web server.
When you run app.run(), it does the following:

  1. Starts a web server on your machine, making it available at 127.0.0.1:5000.
  2. Handles incoming requests from your browser (or any other client).
  3. Routes the request to the correct view function in your Flask app.
  4. Returns the response (like an HTML page or a message) back to the client.

Preamble : Why You Should NOT Use the Flask Built-in Server for Production

While Flask's built-in server is great for development, it's not designed for production.
Here's why you should avoid using it for a live website:

  • Single-threaded (Handles One Request at a Time)
    The built-in server is single-threaded, which means it can only handle one request at a time. This works fine if only one person is using the app. But if multiple people visit your site, the server has to queue the requests. This can lead to slow response times or even crashes.
  • Slow and Not Optimized
    The built-in server is not optimized for speed or handling heavy traffic.
    It's designed to be simple, not fast or powerful. Imagine your app is doing complex tasks, like processing large files or making multiple external API calls — the server could become very slow and unresponsive.
  • No Security Features
    The built-in server doesn't have important security features that a production server needs, like:
    • SSL/HTTPS for secure connections.
    • Rate limiting to prevent too many requests from a single user.
    • Load balancing to distribute the work across multiple servers.
    • Automatic recovery if the server crashes.
    • This means if you use the built-in server for a real website, it could be vulnerable to attacks.

Preamble :WSGI and Gunicorn: How Flask Handles Production

When you're building a Flask app, running it locally with app.run() works great for testing and development.
But once you're ready to show your app to the world, you need a better and more reliable setup.
That's where WSGI and Gunicorn come into play.

What is WSGI ?

WSGI == Web Server Gateway Interface. It's not a tool or a software — it's a standard or protocol that explains how web servers and Python apps (python apps ! == web servers) should communicate.

Why WSGI ?

Web servers like Nginx or Apache are great at handling internet traffic, but they can't run Python code directly.

Flask apps are written in Python, so we need a middleman that can talk to both the web server and the Flask app.

This 'middleman' is WSGI! —> a standard that helps web servers send requests to your Flask app and receive responses back.

So what is Gunicorn ?

Gunicorn (short for Green Unicorn) is a WSGI server. It knows how to understand both sides:

  • What the web server says (incoming HTTP requests)
  • What your Flask app responds with (Python-generated responses)

So: Gunicorn sits between your app and the outside world, receiving incoming requests and sending them to your Flask app using WSGI.
Then it returns the response to the user.

Gunicorn is built for production!:

  • It is Fast and reliable
  • It is Able to handle multiple users at once
  • It is Crash-safe — if one worker crashes, others continue running

Prepare your project to use gunicorn

So we can therefore look at how to set up your flask project to use gunicorn:

  • Make sure you have your virutal environment running and your project loaded in VS Code
  • Install gunicorn with running pip install gunicorn
  • Let's say your python file is called "app.py" then you can run the flask app in the terminal using: gunicorn app:app --bind 127.0.0.1:8000 -> which tells Gunicorn to serve the app at localhost on port 8000.

Note:: We also will continue to use gunicorn as render (the hosting platform) requires it ;)

In order for your application to be hosted properly on the Render Hosting Platform, you will also need to maintain a file which lists all the python modules/packages in the root of your project.
This can be easily accomplished by running the following command in the VS Code terminal:
pip freeze > requirements.txt
Note: whenever you add new modules/packages to youtr project thereafter, you will need to update the requirements.txtfile.

Ensure to keep the environment variables from your .env file up to date...

Finally - in order for your application to run correctly on the Render platform - instead of using:


     if __name__ == "__main__":
        app.run()

Please use:


  if __name__ == "__main__":
    #app.run()
    port = int(os.environ.get("PORT", 10000))
    app.run(host="0.0.0.0", port="port")

Why - well because the Render Platform will require the host to be 0.0.0.0 and the port number to be predetermined by them (Render), or if not will be allocated to be 10000. Also ensure to remove the debug=true property within the app.run()

It is highly advisable that you isolate your project that you want publically hosted to be in a new github repository on its own or to be on a unique branch.
Remember to please not commit and push your .env file.
